# Fix Plan — ISSUE-002

## Employee PII and payroll data are exposed to unauthenticated callers and written to application logs

> Require every caller of employee, payroll, scheduler and department data to authenticate through a framework-level security layer instead of every endpoint being open to anyone, and stop writing personal and salary data into application logs.

## 1. Remediation approach

Apply the CWE-306 canonical_approach at the layer the root cause actually names: no module declares a Spring Security dependency or filter chain, so every controller in every business service is dispatched for anonymous callers. Introduce a deny-by-default Spring Security filter chain in each business service that reaches employee or payroll data (employee-service, sheduler-service, report-service, department-service) rather than an ad-hoc check inside individual handlers, so authentication is enforced once per service instead of per endpoint. Pair this with the related CWE-532 pattern at the specific sinks the root cause identifies: stop passing whole Employee/DepartmentResponse/EmployeeSalaryResponse objects and raw search parameters to the logger, logging identifiers instead. This targets the actual root cause - the complete absence of a security layer - rather than only the single export endpoint named in the issue's steps to reproduce.

**Catalog pattern (`CWE-306`):** Missing Authentication for Critical Function

## 2. Alternatives considered

- Check a hardcoded header or shared secret inside each controller method - rejected because the CWE-306 catalog explicitly names handler-local secret checks as an anti-pattern; they do not establish a real authenticated principal and would have to be duplicated correctly in every handler.
- Add authentication only to GET /api/v1/export, the endpoint named in the issue's steps to reproduce - rejected because the catalog's anti-pattern list specifically warns against securing the named endpoint while leaving structurally identical sibling endpoints (GET /api/v1/employee, GET /api/v1/employee/{id}, GET /api/v1/department/salary/{minSalary}, POST /api/v1/employee) open on other services.
- Lower the affected log statements from INFO/TRACE to DEBUG without removing the sensitive fields - rejected because the CWE-532 catalog entry names this an anti-pattern; the sensitive object is still passed to the logger and still appears whenever that level is enabled.

## 4. Risks to watch

- No identity provider, credential format, or role model is defined anywhere in the current source; each new SecurityConfig above will need an explicit, approved decision on how a caller actually authenticates (e.g. an interim framework-default mechanism versus the platform's eventual chosen identity provider) before an implementation can be more than a stopgap.
- Restricting GET /api/v1/export and GET /api/v1/department/salary/{minSalary} to a privileged role (called for in the root cause's Expected Behavior) needs the role/permission model itself, which is the CWE-862 catalog gap recorded below, not just an authenticated-vs-anonymous check.
- Securing report-service and department-service also secures the service-to-service calls report-service makes to department-service only if a service credential is introduced for that call; adding a deny-by-default filter chain without one would make report-service's own WebClient call to department-service start failing.
- The root cause and blast radius reports also name configuaration-server and discovery-service as reachable without credentials (config values and the Eureka registry/dashboard), but neither report cites a specific file/line defect in those two services, so they are not included in affected_files above; they need their own infrastructure-configuration remediation (Spring Cloud Config authentication and property encryption, Eureka registration/dashboard credentials) tracked separately from this application-code plan.

## 5. How the fix must be verified

1. Compile employee-service, sheduler-service, report-service and department-service after the security dependency and configuration changes.
2. Verify an unauthenticated request to each of GET /api/v1/employee, GET /api/v1/employee/{id}, GET /api/v1/employee/search, POST /api/v1/employee, GET /api/v1/export and GET /api/v1/department/salary/{minSalary} now receives an authentication failure instead of the previous data response.
3. Once an authorization design exists, verify an authenticated but ordinary-role caller cannot reach GET /api/v1/export or GET /api/v1/department/salary/{minSalary}, while the designated privileged role can.
4. Inspect application logs while creating, searching, exporting and retrieving salary data, and confirm employee objects, raw search values, addresses, phone numbers and salary values no longer appear.
5. Confirm report-service's existing call to department-service still succeeds once department-service requires authentication, i.e. that a service credential was added rather than the call simply starting to fail closed.

_The Fixer's verification report must address every step above, or explain why a step could not be run (e.g. it needs a live dependency unavailable in the isolated build sandbox)._

## 6. Open questions

- Catalog gap: CWE-862 (Missing Authorization) has no catalog entry. Restricting payroll/salary endpoints to a privileged role - called for by the root cause's Expected Behavior - needs an approved authorization pattern before that part of the design can be implemented, not just this plan's authentication layer.
- Catalog gap: CWE-359 (Exposure of Private Personal Information) has no catalog entry. Replacing GET /api/v1/employee's direct Employee entity response with a least-data DTO needs an approved data-minimization pattern; this plan's affected_files close the authentication hole but do not by themselves stop every field from being returned to whichever caller is authenticated.
- The identity provider, token/credential format, and any service-to-service credential are not defined in the Phase A inputs; each new SecurityConfig above is a placeholder for whatever mechanism is approved, not a specific proposed mechanism.
- configuaration-server and discovery-service hardening (credentialed registration, dashboard auth, {cipher} secret encryption) is called for by the root cause's Expected Behavior but has no file-level evidence in this plan's inputs, so it is flagged here rather than included in affected_files.
