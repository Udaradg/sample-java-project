## 1. Remediation approach

Apply the CWE-306 catalog pattern at the Spring Security layer: introduce a deny-by-default filter chain and explicitly allow only designated operational endpoints, then require authenticated principals for employee and payroll handlers. The eventual authorization design must limit payroll exports and salary data to an explicit privileged role, while sensitive logs are reduced to identifiers in line with the related CWE-532 catalog pattern. This closes anonymous access at the shared enforcement layer rather than adding inconsistent ad-hoc checks in individual controllers.

**Catalog pattern (`CWE-306`):** Missing Authentication for Critical Function

## 2. Alternatives considered

- Checking a hardcoded header or shared secret inside each controller method - rejected because CWE-306 explicitly identifies handler-local secrets as an anti-pattern and they do not establish a consistent authenticated principal.
- Securing only the export endpoint - rejected because structurally similar employee, department, scheduler, and write paths would remain anonymous.
- Lowering log levels without removing sensitive fields - rejected because CWE-532 identifies that as an anti-pattern; data must not be passed to logging calls.

- The root-cause report identifies additional externally reachable services and configuration infrastructure beyond the listed affected files; a full platform remediation cannot safely be confined to these files.

## 5. How the fix must be verified

1. Compile every affected service after the approved security dependencies and configuration are applied.
2. Verify an unauthenticated request to each sensitive employee, payroll, scheduler, and department endpoint receives an authentication failure and cannot read or write data.
3. Verify an authenticated ordinary role cannot access payroll exports or salary endpoints, while the designated privileged role can access only its approved operations.
4. Inspect application logs while creating, searching, exporting, and retrieving salary data to confirm employee objects, raw search values, addresses, phone numbers, and salary values are absent.
5. Verify service-to-service requests use the approved service identity and retain expected application behavior.

_The Fixer's verification report must address every step above, or explain why a step could not be run (e.g. it needs a live dependency unavailable in the isolated build sandbox)._
