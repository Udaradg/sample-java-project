## 3. Why this is the smallest correct diff

Apply the CWE-306 canonical_approach at the layer the root cause actually names: no module declares a Spring Security dependency or filter chain, so every controller in every business service is dispatched for anonymous callers. Introduce a deny-by-default Spring Security filter chain in each business service that reaches employee or payroll data (employee-service, sheduler-service, report-service, department-service) rather than an ad-hoc check inside individual handlers, so authentication is enforced once per service instead of per endpoint. Pair this with the related CWE-532 pattern at the specific sinks the root cause identifies: stop passing whole Employee/DepartmentResponse/EmployeeSalaryResponse objects and raw search parameters to the logger, logging identifiers instead. This targets the actual root cause - the complete absence of a security layer - rather than only the single export endpoint named in the issue's steps to reproduce.

**Catalog pattern (`CWE-306`):** Missing Authentication for Critical Function

## 5. Residual risk

A human must approve the real identity provider before this is more than a placeholder.
- Plan risk #3: securing department-service without also adding a service credential to report-service's own WebClient call (in EmployeeReportServiceImpl.getEmployees(), calling departmentConfigUrl.getDepartmentUrl()) will make that internal call start receiving 401s from department-service's new filter chain. Adding such a credential was not in this plan's affected_files, so it is not implemented here and is called out for the next verification stage to check live.
- CWE-862 (Missing Authorization) has no catalog entry, so GET /api/v1/export and GET /api/v1/department/salary/{minSalary} are now authenticated but not role-restricted -- any authenticated caller, not just a privileged one, can still reach payroll/salary data. This matches the plan's explicit scope boundary, not an oversight.
- CWE-359 (data minimization) has no catalog entry either, so GET /api/v1/employee/{id} and similar still return the full Employee/EmployeeResponse entity to any authenticated caller.
