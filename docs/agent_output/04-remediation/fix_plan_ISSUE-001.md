## 1. Remediation approach

Apply the CWE-770 catalog pattern by replacing unbounded repository reads with database-backed bounded retrieval. The scheduler REST path must use Spring Data Pageable with a server-enforced maximum page size, while the scheduled gender operation must retrieve only matching records through a database query. The report flow must process employee data in pages or as a stream and avoid retaining a complete result set and workbook payload together, so memory use does not scale with the entire collection.

**Catalog pattern (`CWE-770`):** Allocation of Resources Without Limits or Throttling

## 2. Alternatives considered

- Adding an uncapped client-controlled size parameter - rejected because the CWE-770 catalog identifies this as an anti-pattern: callers could still request an effectively unbounded page.
- Only fixing the public scheduler endpoint - rejected because the same unbounded read is reachable from the scheduled job and the catalog requires equivalent reachable paths to be addressed.
- Catching OutOfMemoryError or increasing heap size - rejected because this treats the consequence rather than putting a bound on database reads and response assembly.

## 4. Risks to watch

- Pagination changes the scheduler endpoint response contract and requires an explicit default and maximum page size that clients can handle.
- A truly large XLSX export may require a streaming response and workbook implementation; the exact controller and repository changes must be determined against current source during an approved implementation.
- The report's department lookup and in-memory nested join remain performance considerations even after employee retrieval is bounded.

## 5. How the fix must be verified

1. Compile the scheduler-service and report-service modules after the exact bounded-query contract changes are implemented.
2. Seed more records than the configured maximum page size and verify the scheduler endpoint returns only the requested bounded page while rejecting or clamping oversized size requests server-side.
3. Run the Women's Day job with mixed genders and verify it obtains only matching employees without calling an unfiltered findAll path.
4. Exercise the export with a dataset larger than one processing chunk and verify the generated output contains expected rows while heap usage does not require materializing the entire collection in a single list.

_The Fixer's verification report must address every step above, or explain why a step could not be run (e.g. it needs a live dependency unavailable in the isolated build sandbox)._
