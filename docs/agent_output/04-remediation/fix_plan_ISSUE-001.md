# Fix Plan — ISSUE-001

## Unbounded repository findAll() reads whole collections into memory across multiple services

> Make every employee read go through the database with a size limit or a matching filter, instead of pulling the whole employee collection into memory first, so a single request or scheduled run can no longer scale a service's memory and database load with however large the collection has grown.

## 1. Remediation approach

Apply the CWE-770 canonical_approach at each of the two unbounded findAll() sinks named in the root cause. In sheduler-service, replace EmployeeSchedulerServiceImpl.getAllEmployees()'s direct findAll() with a Pageable-backed query returning Page<Employee>, capped server-side, and give the Women's Day job its own database-side gender query so it stops loading every employee before filtering in Java. In report-service, replace EmployeeReportServiceImpl's full findAll() + full-list join + fully-buffered XLSX (getEmployees()/generateExcelFile()) with paged repository reads whose rows are written to the workbook and the HTTP response as they are produced, so no single in-memory collection ever holds the complete employee set, salary-response list, or workbook byte array at once. Both changes push the bound to the database query itself, which is what the catalog requires, rather than adding an unenforced size hint or catching the eventual OutOfMemoryError.

**Catalog pattern (`CWE-770`):** Allocation of Resources Without Limits or Throttling

## 2. Alternatives considered

- Add a client-supplied page-size query parameter that the server does not cap - rejected: the CWE-770 catalog names this an anti-pattern, since a caller could still request an effectively unbounded page.
- Bound only the GET /api/v1/employee REST path and leave WomenDaySchedulerImpl calling the same getAllEmployees() - rejected: the catalog explicitly flags leaving an equivalent unbounded call reachable from a scheduled job, and the job reaches the identical findAll() sink today.
- Keep collecting the full EmployeeSalaryResponse list and the full XSSFWorkbook in memory, and only add a try/catch around the export or raise heap size - rejected: this treats the eventual failure rather than bounding the read and the response assembly, so cost still scales with collection size.

## 4. Risks to watch

- Changing GET /api/v1/employee from List<Employee> to Page<Employee> is a response-shape change for any existing caller; the default and maximum page size need to be picked deliberately, not left implicit.
- A streaming workbook (e.g. SXSSFWorkbook) trades random cell access for bounded memory - any later code that expects to re-read a row already flushed to disk within the same request will not be able to.
- report-service's department lookup and in-memory nested join (each employee page against every department) remain a secondary cost even once the employee read itself is bounded; a large department list still multiplies per page.
- report-service/src/main/java/com/aura/vihanga/reportservice/repository/EmployeeReportRepository.java has a pre-existing compile defect that is unrelated to this plan: its findByDepartment(String department) method uses List<Employee> without an import for java.util.List. This was confirmed present at HEAD, independent of any patch. Because it lives in the same Maven module as EmployeeReportServiceImpl.java, report-service will fail to compile until that import is added - which is outside this plan's affected_files and should be tracked as its own defect rather than folded into this CWE-770 patch.

## 5. How the fix must be verified

1. Compile the sheduler-service and report-service modules after the bounded-query and streaming-export changes.
2. Seed more employee records than the configured maximum page size and confirm GET /api/v1/employee returns only the requested bounded page, and that requesting an oversized size is clamped or rejected server-side rather than honoured.
3. Exercise the Women's Day job logic with a mixed-gender seed set and confirm it now calls only the gender-filtered repository query, never the unfiltered findAll path.
4. Exercise GET /api/v1/export with more employees than one processing page and confirm the generated workbook still contains every expected row while no single collection in the implementation holds the full employee set at once.
