## 3. Why this is the smallest correct diff

Apply the CWE-770 canonical_approach at each of the two unbounded findAll() sinks named in the root cause. In sheduler-service, replace EmployeeSchedulerServiceImpl.getAllEmployees()'s direct findAll() with a Pageable-backed query returning Page<Employee>, capped server-side, and give the Women's Day job its own database-side gender query so it stops loading every employee before filtering in Java. In report-service, replace EmployeeReportServiceImpl's full findAll() + full-list join + fully-buffered XLSX (getEmployees()/generateExcelFile()) with paged repository reads whose rows are written to the workbook and the HTTP response as they are produced, so no single in-memory collection ever holds the complete employee set, salary-response list, or workbook byte array at once. Both changes push the bound to the database query itself, which is what the catalog requires, rather than adding an unenforced size hint or catching the eventual OutOfMemoryError.

**Catalog pattern (`CWE-770`):** Allocation of Resources Without Limits or Throttling

## 6. Open questions

- This patch was previously attempted against an earlier HEAD and failed to compile only because of a pre-existing, unrelated missing `java.util.List` import in report-service/src/main/java/com/aura/vihanga/reportservice/repository/EmployeeReportRepository.java. That import is present at the current HEAD (fixed by a separate commit), so this re-drafted patch no longer touches or depends on that file being broken.
- Re-verifying against the current HEAD, the patch still fails to compile, but for a different and confirmed environment reason: the only JDK available on this machine is Amazon Corretto 25 (JAVA_HOME points at jdk25.0.1_8), while this project targets Java 17 and relies on Lombok (@Slf4j, @Data, @Builder, @AllArgsConstructor) for generated code. To isolate the cause, the same `mvnw compile` was run against the unmodified report-service module and, separately, the unmodified employee-service module straight off HEAD, with no patch applied at all: both fail with the identical class of errors (`cannot find symbol: variable log`, missing Lombok-generated getters/builders/constructors). This confirms Lombok annotation processing is not running under the JDK 25 toolchain currently on this machine, project-wide, independent of this or any other patch. This is the exact 'Known caveat' the Fixer skill documents (JDK far newer than the Java 17 target silently breaking Lombok) and is an environment gap, not a defect introduced by this diff.
