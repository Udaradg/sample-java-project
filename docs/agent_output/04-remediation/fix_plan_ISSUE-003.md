## 1. Remediation approach

Apply the CWE-943 canonical_approach directly at the sink the root cause names: replace EmployeeSearchRepository.searchEmployees's StringBuilder-assembled BasicQuery with Spring Data's Criteria/Query API. Bind department with Criteria.where("department").is(department) so it can never be interpreted as query structure, and keep the name search substring-based but wrap the caller's value in Pattern.quote(...) inside the regex Criteria so it is matched as literal text, not caller-controlled regex or operator syntax. This changes the query-construction mechanism itself - the actual root cause - rather than trying to filter or escape specific characters out of the input, which the catalog identifies as insufficient. Complementary controller-side validation narrows what ever reaches the repository, but the repository-level rewrite is what removes the injection primitive.

**Catalog pattern (`CWE-943`):** Improper Neutralization of Special Elements in Data Query Logic (NoSQL/SQL Injection)

## 2. Alternatives considered

- Escape or blacklist quotes, braces and $ characters before building the same BasicQuery string - rejected because the CWE-943 catalog identifies character filtering as insufficient compared with parameterized criteria, and the injected payloads in the issue use ordinary quote/brace characters that a legitimate name could also contain.
- Add only a length limit or a rate limit in front of the existing string-built query - rejected because it may reduce abuse volume but leaves the query-construction sink itself injectable at any rate.
- Keep BasicQuery and wrap the construction in a try/catch that discards malformed queries - rejected because the tainted string still reaches the query sink for any payload that remains syntactically valid JSON, which includes the documented injection payloads.

## 4. Risks to watch

- Pattern.quote(...) turns the name parameter from caller-supplied regex syntax into a literal substring match; if any legitimate caller intentionally relies on passing real regex syntax through this endpoint, that usage needs a separate, deliberately designed search capability rather than this endpoint.
- Controller-side validation may need an explicit permitted-character set decision (the issue's benign examples are ordinary names); it should reject rather than silently strip disallowed input, so validation failures are observable.
- ISSUE-002 leaves this endpoint reachable without authentication until its own plan is approved and implemented; this plan closes the injection primitive but not the anonymous-access exposure.

## 5. How the fix must be verified

1. Compile employee-service after the repository and controller changes.
2. Replay the benign request name=Ann and confirm the same matching employees are returned as before, under literal substring semantics.
3. Replay the documented name and department injection payloads from the issue and confirm they are treated as literal values - no broadened result set, and no injected operator is honoured.
4. Confirm overly long or disallowed-character search values are rejected at the controller boundary, and that the repository's query construction uses Criteria regardless of what the validation layer does.
5. Inspect employee-service logs for the search path and confirm the constructed query text and raw request values no longer appear.
