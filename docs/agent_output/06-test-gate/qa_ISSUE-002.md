## 1. What the new test proves

Proves the CWE-532 half of the paired ISSUE-002 fix (the CWE-306 half -- the new deny-by-default SecurityFilterChain -- is a Spring Security filter chain that needs a live @WebMvcTest/@SpringBootTest context this sandbox cannot start, so it is not covered by this mocked unit test; see Residual risk in the fix report). Replays an adversarial createEmployee call carrying a PII-bearing Employee (a sentinel name and department chosen to be unmistakable if leaked) and a benign searchEmployees call carrying raw name/department parameters, then inspects the real Logback events captured by a ListAppender attached to EmployeeController's actual Logger. Asserts the sentinel PII values and the raw search parameters never appear in any logged message, while an identifier-free operational message is still emitted -- this is the exact removal (log.trace(...) losing the `employee`/`name`/`department` arguments) the fix diff makes.

**Mocking strategy:** EmployeeService is Mockito-mocked (Mockito.mock(EmployeeService.class)) and injected into a plain `new EmployeeController()` instance via ReflectionTestUtils.setField, since the field is @Autowired-only with no setter/constructor and this sandbox has no embedded-MongoDB/Testcontainers dependency to run a live-repository or live-security-context test. Log output is captured with a real ch.qos.logback.core.read.ListAppender attached directly to LoggerFactory.getLogger(EmployeeController.class) -- the same singleton the Lombok-generated `log` field resolves to at runtime -- so the assertion is on what Logback actually emits, not on a mocked logger call.
