## 1. What the new test proves

Replays the reported operator-injection payload from docs/agent_output/02-root-cause/root_cause_ISSUE-003.md (name="x' } }, { 'name': { $ne: '", department="' }, 'name': { $ne: '") through EmployeeSearchRepository.searchEmployees and captures the real org.springframework.data.mongodb.core.query.Query handed to MongoTemplate.find(...). It asserts the bound BSON shape: 'name' must be a java.util.regex.Pattern whose pattern() equals Pattern.quote(name) exactly (the whole payload survives as an escaped literal, proving it cannot close the regex or inject operators), and 'department' must be the exact raw string bound as a plain equality value (not truncated or reinterpreted as JSON/operator syntax). A second case replays a benign input (name=Ann, department=Engineering) and asserts the same literal-regex/equality shape with no extra query keys. Empirically verified against this repo's actual spring-data-mongodb 3.4.12 jar (via a throwaway classpath probe) that on the pre-patch StringBuilder+BasicQuery construction, queryObject.get("name") for this payload is an org.bson.Document (not a Pattern) and department is silently mangled to an empty string rather than preserved verbatim -- so this test fails against the vulnerable code and passes only against the Criteria/Query-based fix.

**Mocking strategy:** MongoTemplate is Mockito-mocked (Mockito.mock(MongoTemplate.class)) and injected into a plain `new EmployeeSearchRepository()` instance via ReflectionTestUtils.setField, since the field is @Autowired-only with no setter/constructor and this sandbox has no embedded-MongoDB/Testcontainers dependency to run a @DataMongoTest-style test. The Query argument passed to the mocked find(...) is captured with an ArgumentCaptor<Query> and inspected via its real getQueryObject() Document/Pattern values -- no live MongoDB connection is needed or used.
