## MongoDB (NoSQL) injection in the employee search endpoint via string-concatenated BasicQuery

> ⛔ Blocked — not safe to ship.

## Chain of custody

The root-cause report (docs/agent_output/02-root-cause/root_cause_ISSUE-003.md, Critical severity, High confidence) traced this to EmployeeSearchRepository.searchEmployees concatenating untrusted name/department request values into a MongoDB BasicQuery string instead of binding them, so quote/operator characters in caller input could alter query structure. The Fixer drafted a diff matching that plan (docs/agent_output/04-remediation/fix_ISSUE-003.md) and recorded Status: Compile Failed, with its Open Questions section already identifying the failure as an unrelated Lombok/JDK-25 toolchain gap in ExcelUploadImpl.java, a file this diff never touches, reproduced against an unmodified employee-service checkout. Verification then ran three independent checks, each explicitly re-triggered this session against the current diff/HEAD after a line-level edit (an explicit reassignment on the department Criteria.and(...) call) and reconfirmed unchanged: re-scan (docs/agent_output/05-verify/rescan_ISSUE-003.md) found FIXED at High confidence — the query is now built via bound Criteria/Pattern.quote with no text-parsing step caller input can exploit, and the specific line edit was confirmed by decompiling the project's actual spring-data-mongodb-3.4.12.jar to be functionally neutral (Criteria.and() shares its parent's criteriaChain by reference regardless of reassignment); red-team recon (docs/agent_output/05-verify/redteam_ISSUE-003.md) found NO_BYPASS_FOUND at Medium confidence across six attempted vectors (operator injection, regex/ReDoS, Pattern.quote \E escape, field-name injection, allowlist bypass, type confusion), all blocked by construction; behavior guard (docs/agent_output/05-verify/behavior_ISSUE-003.md) found BEHAVIOR_CHANGED at High confidence with 4 out-of-scope changes — the repository's per-request INFO log and the controller's TRACE log both disappear silently with no mention in the fix plan, an empty `?department=` parameter that previously behaved as no-filter now returns HTTP 400, and the new allowlist rejects previously-accepted characters (e.g. `R&D`, underscores) beyond what the plan's own flagged open question about the character set anticipated concretely.
