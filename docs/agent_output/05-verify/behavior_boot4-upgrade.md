## 1. In-scope changes (the intended fix)

- The Java 17 to 21 and Spring Boot 3.5.0 to 4.1.1 platform changes, including the compiler release change and Java 21 container base image.
- Jackson 3 migration: ObjectMapper and JavaTimeModule are replaced by JsonMapperBuilderCustomizer and tools.jackson APIs while ISO date formatting, NON_NULL inclusion, and non-indented output remain configured.
- Boot 4 framework relocations: Health and HealthIndicator move to org.springframework.boot.health.contributor; test slices move to the modular webmvc-test and data-jpa-test starters; MockBean becomes MockitoBean.
- Security test wiring: spring-boot-starter-security-test restores the SecurityContext bridge required by @WithMockUser without changing the production SecurityFilterChain.
- Framework-owned actuator health output and authentication error timestamp formatting changes acknowledged by the migration's runtime comparison.
- All 19 tests passed after the security-test starter correction, and all 15 probes preserved their expected HTTP status, authentication boundary, and application-owned 404/validation semantics.

### Why these changes are in scope

The platform, compiler, dependency, and package changes are direct consequences of the approved Boot 4 and Java 21 migration. The Jackson edits preserve the application's stated serialization policy: ISO date values, `NON_NULL` inclusion, and compact output. The security-test dependency change is also in scope because it restores the test harness needed to exercise the unchanged production security chain; without it, five authenticated test requests incorrectly reached production code as anonymous requests.

### Why this is behavior, even though the status stayed 400

An HTTP status describes only the coarse result. A client that deserializes `application/problem+json` into a required `type` field, compares a schema, signs the complete payload, or uses property presence for routing can observe the removed member. Property reordering alone is usually harmless for JSON semantics, but the missing `type=about:blank` member is a schema-level difference and is therefore correctly classified as an out-of-scope behavior change.

Because a strict behavior guard treats response schema changes as behavior even when HTTP statuses are stable, the final classification remains BEHAVIOR_CHANGED. The health and 401 differences were explicitly anticipated as framework-owned migration effects; the removed problem-details type member is the remaining client-visible contract risk not explicitly approved in the plan.

## 4. Impact assessment

The migration is operationally green for the exercised paths, but it is not contract-neutral. The affected path is the framework-generated missing-parameter error, not the application's `ErrorResponse` model or the employee business operations. The likely impact is limited to strict API consumers, generated clients, schema validators, contract tests, and middleware that expects the RFC 9457-style `type` member to be present.

The report does not establish whether any deployed consumer relies on that member. That is a release decision, not something the static behavior guard can infer. The migration should therefore either explicitly accept and document the Boot 4 problem-details shape, add a compatibility handler/normalizer for missing-parameter errors, or block release until consumer contract tests confirm that the field is not required.

## 5. Verification limits and next actions

- The comparison used recorded baseline and patched probes; it was not a live deployment check from the current checkout.
- The 19-test result establishes test-suite parity for the covered tests, not compatibility with every external client.
- The health payload grew and map-backed properties reordered; consumers should parse fields rather than compare raw JSON strings.
- The 401 timestamp changed representation to UTC `Z`; clients should treat it as an RFC-compliant timestamp rather than depend on the old offset format.

Recommended next action: add a focused contract test for the missing-query-parameter response that states whether `type` is required. If it is required, implement and verify an application-owned compatibility response; if it is optional, update the migration plan and consumer documentation to approve the observed Boot 4 behavior.

## 2. Out-of-scope changes

The plan expected framework-owned body differences generally, but did not explicitly approve removal of this response field; strict clients that validate this payload can observe a contract change.

## 3. Reasoning

The migration record provides a like-for-like baseline/final comparison: 19 tests passed on both versions and all 15 probes returned the same HTTP statuses. The five business read paths, authentication boundary, unknown-employee 404 path, and invalid-create validation status remained operational. The application's ErrorResponse-backed responses retain their declared fields; their LocalDateTime timestamps differ naturally because the two runtime captures occurred at different times. Because a strict behavior guard treats response schema changes as behavior even when HTTP statuses are stable, the final classification remains BEHAVIOR_CHANGED. The health and 401 differences were explicitly anticipated as framework-owned migration effects; the removed problem-details type member is the remaining client-visible contract risk not explicitly approved in the plan.
