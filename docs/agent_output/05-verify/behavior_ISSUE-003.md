## 2. Out-of-scope changes

The fix plan's risk notes flag that the *character-set* decision for validation needed to be made, but do not call out this specific behavior change for a previously-valid empty value, and don't state whether narrowing was meant to reach this edge case.

## 3. Reasoning

The plan's stated scope covers two things: (1) rewrite the repository query construction to Criteria/Query, and (2) add complementary controller-side validation. Both of those specific mechanisms are present in the diff and match the plan closely enough to count as in-scope. However, the diff does more than that: it silently removes two log statements (one INFO in the repository showing the constructed filter, one TRACE in the controller showing raw request parameters) that the plan never mentions touching, and it changes response behavior for at least one previously-valid input class (empty-string department) in a way the plan's risk notes gesture at generally ('an explicit permitted-character set decision') but do not concretely specify or acknowledge. Per this check's own constraint, a change that isn't traced to planned_change belongs in out_of_scope_changes regardless of whether it is small or arguably beneficial (e.g. removing a log line that echoed user input could itself be seen as good security hygiene) — that judgment is explicitly not this check's to make. None of the out-of-scope items reopen the CWE-943 injection path re-scan and red-team already assessed; they are observability (logging) and input-acceptance (validation strictness) changes only.
