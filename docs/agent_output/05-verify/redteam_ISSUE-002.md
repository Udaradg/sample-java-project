# Red-team Recon — ISSUE-002

## Employee PII and payroll data are exposed to unauthenticated callers and written to application logs

> The deny-by-default rule itself works -- a request with no credentials is rejected everywhere -- but every one of the four newly-secured services can be authenticated against using Spring Boot's single framework-generated default account, whose password is printed to that service's own startup logs because no real user store was ever configured, so the barrier is real but the credential behind it is a de facto shared secret anyone with log access already has.

## 2. Bypasses found

### Every one of the four newly-secured services relies on httpBasic() with no UserDetailsService/InMemoryUserDetailsManager/AuthenticationProvider or spring.security.user.* property configured anywhere in the codebase or its Spring Cloud Config source. Spring Boot's security auto-configuration therefore generates a single default account ('user') with a random password printed to that service's own startup console/log on every restart. Anyone able to read that output -- a CI/CD console, a container/orchestrator log aggregator, `docker logs`, `kubectl logs`, or any other log consumer, none of which is the trust boundary CWE-306 (or this fix's own risk notes) intended to gate -- obtains a fully valid, unrestricted credential for every endpoint in that service, since the filter chain only checks `anyRequest().authenticated()` with no per-role restriction. It is also a single shared account, so a use leaves no per-caller identity or audit trail.

**Severity:** High

```
Grep across the repository and every application.properties (including configuaration-server's) for UserDetailsService, InMemoryUserDetailsManager, AuthenticationManager, AuthenticationProvider, and spring.security.user returns zero matches. Given spring-boot-starter-security on the classpath and HttpSecurity.httpBasic() enabled with no custom user store, Spring Boot's UserDetailsServiceAutoConfiguration is documented to create exactly one InMemoryUserDetailsManager user with a SecureRandom-generated password logged at startup. `curl -u user:<the logged password> http://<service>/api/v1/employee` (or any endpoint in that service) would authenticate successfully, since no role or authority is checked beyond being authenticated.
```

## 3. Reasoning

The patch correctly implements a framework-level, deny-by-default filter chain rather than an ad-hoc per-handler check, and applies it uniformly to every endpoint in each named service rather than only the one the issue cited -- both of the catalog's named anti-patterns are avoided. The gap is one level deeper: the plan's own risk notes already flag that 'no identity provider, credential format, or role model is defined anywhere,' and the diff does not resolve that -- it ships httpBasic() with nothing behind it, so Spring Boot's framework default silently fills the gap with a single, log-exposed account. That is functionally a shared, discoverable secret standing in for real authentication, which is close in spirit to the catalog's own anti-pattern of 'checking a hardcoded header or shared secret' even though the mechanism (a framework auto-generated value) differs from a developer-hardcoded one. This is a genuinely distinct vector from the original finding -- the original defect was zero credential required at all; this one is that the only credential available is not meaningfully secret.

## Residual risk

- report-service's and (separately, undocumented by the plan) employee-service's own internal WebClient calls to department-service carry no credentials at all; once department-service enforces this same httpBasic() rule, those calls will start failing with 401 -- a reliability regression distinct from the credential-strength issue above, detailed in the behavior-guard report.
- configuaration-server and discovery-service remain completely unauthenticated, as explicitly scoped out by the fix plan.
