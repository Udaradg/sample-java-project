## 2. Reasoning

The root cause was EmployeeSearchRepository.searchEmployees building `{ 'name': { $regex: '<name>' } , 'department': '<department>' }` via StringBuilder.append and handing the raw string to `new BasicQuery(...)` — request values influenced query structure, not just query values. The patched code replaces this entirely: `Criteria.where("name").regex(Pattern.quote(name))` and `criteria.and("department").is(department)` passed to `new Query(criteria)`. Both parameters are now bound as literal BSON values by the Mongo driver rather than being parsed as characters inside a hand-assembled document string, so there is no longer a text-parsing step in which caller input can close a brace, inject a `$where`/`$ne`/`$gt` operator key, or otherwise alter query shape. `Pattern.quote(name)` additionally neutralizes name as a regex — `.` `*` `^` `$` etc. become literal characters for the substring match rather than being interpreted as regex metacharacters, closing the secondary regex-injection angle the same sink allowed. This is a mechanism-level fix (matches the CWE-943 canonical_approach of parameterised criteria), not a character filter or escape layered on top of the same concatenation, so it is not merely hiding the old signature. Detection signatures BasicQuery/StringBuilder/append/log-of-tainted-filter are all gone from the sink; Criteria and Pattern.quote are present as expected. The @RequestParam and searchEmployees signatures naturally remain (they are the entry point, not the defect), and @Valid was never the plan's approach so its absence is not a gap.
