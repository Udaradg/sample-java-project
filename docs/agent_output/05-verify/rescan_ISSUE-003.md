## 2. Reasoning

The root cause was EmployeeSearchRepository.searchEmployees building `{ 'name': { $regex: '<name>' } , 'department': '<department>' }` via StringBuilder.append and handing the raw string to `new BasicQuery(...)` -- request values influenced query structure, not just query values. The current patched code replaces this entirely: `Criteria criteria = Criteria.where("name").regex(Pattern.quote(name));` followed by `criteria = criteria.and("department").is(department);` when a department is supplied, passed to `new Query(criteria)`. Both parameters are bound as literal BSON values by the Mongo driver rather than being parsed as characters inside a hand-assembled document string, so there is no text-parsing step in which caller input can close a brace, inject a $where/$ne/$gt operator key, or otherwise alter query shape. Pattern.quote(name) additionally neutralizes name as a regex -- . * ^ $ etc. become literal characters for the substring match rather than regex metacharacters, closing the secondary regex-injection angle the same sink allowed. This is a mechanism-level fix (matches the CWE-943 canonical_approach of parameterised criteria), not a character filter layered on the same concatenation. Detection signatures BasicQuery/StringBuilder/append/log-of-tainted-filter are gone; Criteria and Pattern.quote are present as expected; @RequestParam/searchEmployees remain because they are the entry point, not the defect. This re-run was triggered specifically because the diff changed since the prior report: the department line changed from `criteria.and("department").is(department);` (no reassignment) to `criteria = criteria.and("department").is(department);` (reassigned). I verified this edit's actual effect by decompiling the project's own spring-data-mongodb-3.4.12.jar: Criteria.and(String) constructs a new Criteria via the protected `Criteria(List<Criteria> criteriaChain, String key)` constructor, which stores the *same* criteriaChain List reference (no copy) and appends the new sub-Criteria to it (`this.criteriaChain.add(this)`); getCriteriaObject() then iterates that shared chain regardless of which Criteria object in the chain it is invoked on. So both the old un-reassigned line and the new reassigned line already produced the identical combined query -- department was always bound via .is() and never string-concatenated, in both diff versions. The line edit is therefore a style/idiom correction (making the mutation explicit rather than relying on a shared-list side effect), not a change to whether the injection mechanism is closed. Net effect: the FIXED verdict from the prior (now-stale) report is reconfirmed against the current diff and current HEAD, with the specific edit that prompted this re-run independently confirmed to be functionally neutral to the security-relevant behaviour.
