## 2. Bypasses found

### The interim authentication credential's fallback default (changeit-interim-credential) is committed in plain text in employee-service/src/main/resources/application.properties. If the operator does not override it via the EMPLOYEE_SERVICE_ADMIN_PASSWORD environment variable at deploy time -- and nothing in the current change detects or warns about this at startup -- the service is 'protected' by a publicly-known, source-controlled password, which is functionally equivalent to CWE-798 (Use of Hard-coded Credentials) layered on top of the CWE-306 fix.

**Severity:** Medium

```
curl -u employee-service-admin:changeit-interim-credential http://localhost:8500/api/v1/employee/{id}  # succeeds if the operator never set EMPLOYEE_SERVICE_ADMIN_PASSWORD
```

## 3. Reasoning

This is not a flaw in the access-control mechanism itself -- Spring Security's deny-by-default filter chain genuinely requires a credential, closing the original 'no authentication at all' defect. The bypass is in the credential's own default value being both weak and public: the fix plan already flagged this as an interim stopgap pending real identity-provider integration, but did not treat the default's public visibility as a distinct, actionable risk. A caller who has simply read this repository (public or otherwise) has everything needed to authenticate.

## Residual risk

- Recommend failing fast at startup if EMPLOYEE_SERVICE_ADMIN_PASSWORD is unset, rather than silently falling back to a known default -- this converts a silent weak-credential deployment into a loud, unmissable configuration error.
- The other five affected services remain fully unauthenticated (out of scope for this diff, already tracked).
