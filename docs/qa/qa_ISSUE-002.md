## 1. What the new test proves

Two assertions using @WebMvcTest (which loads only the web layer, including Spring Security's auto-configured filter chain, with EmployeeService mocked): (1) GET /api/v1/employee/{id} with no credentials now returns 401 Unauthorized -- on the pre-patch code, with no security dependency at all, this same request would have returned 200 with the employee's data, so this assertion would fail against the old code and passes against the patched code; (2) the same request with an authenticated principal (@WithMockUser) reaches the controller and returns 200, proving the fix does not simply block everything but correctly gates on authentication.

**Mocking strategy:** @WebMvcTest(EmployeeController.class) loads only the Spring MVC + Spring Security slice of the application context, not the data/repository layer, so no MongoDB connection is needed -- this workspace has no embedded-MongoDB dependency, so a full @SpringBootTest or @DataMongoTest could not run here. EmployeeService is @MockBean'd since the controller depends on it, but its behaviour is irrelevant to this test -- only whether the request reaches it at all is being verified.
