## 1. Remediation approach

Replace EmployeeSearchRepository.searchEmployees's StringBuilder-built BasicQuery with a parameterised Criteria query, applying the catalog's CWE-943 canonical_approach to this repository's Spring Data MongoDB stack: Criteria.where("name").regex(Pattern.quote(name)), optionally chained with .and("department").is(department), executed via a Query wrapping that Criteria instead of a BasicQuery built from concatenated strings. Pattern.quote() ensures the name value is matched as a literal substring rather than as caller-supplied regex or query-operator syntax, which is what removes the caller's ability to inject structure — not just today's reported payload shapes. The department value is already a scalar match (`.is(...)`), which Criteria binds directly with no string interpolation at all.

**Catalog pattern (`CWE-943`):** Improper Neutralization of Special Elements in Data Query Logic (NoSQL/SQL Injection)

## 2. Alternatives considered

- CWE-89 (classic SQL injection) was detected in the issue text alongside CWE-943, but this codebase has no SQL/JPQL involved — the sink is Spring Data MongoDB's BasicQuery, which is precisely what the CWE-943 catalog entry describes. CWE-89 is not the applicable entry here; it is cited in the issue only as the well-known injection family this bug belongs to.
- Escaping/stripping MongoDB operator characters ($, {, }, ') from the input before concatenation was considered and rejected: the catalog's anti_patterns for CWE-943 flags this explicitly, since it treats today's payload shape as the problem instead of the query-construction mechanism, and is bypassable by any character sequence the escaping logic didn't anticipate.
- Adding authentication to the endpoint (addressing ISSUE-002, the companion unauthenticated-access issue) was considered but rejected as a substitute fix here: it would reduce who can reach the sink, but the query itself would still be injectable by any authenticated caller, so it does not address this issue's root cause. It remains valid as its own, separate fix.

## 4. Risks to watch

- Pattern.quote(name) makes the name search a literal substring match rather than a caller-supplied regex — the issue's own Expected Behavior section explicitly calls for this, so it is the intended behaviour change, not a side effect, but note it for the reviewer in case any legitimate caller currently relies on passing real regex syntax through the name parameter.
- The existing log.info call logs the constructed filter; once the filter is a Criteria/Query object rather than a String, the log statement needs an equivalent human-readable form (e.g. query.getQueryObject().toJson()) so the log's diagnostic value is preserved rather than silently dropped.
- This fix addresses the injection only. It does not address ISSUE-002 (endpoint has no authentication) or the unbounded-read pattern flagged elsewhere in the register — those remain separate, already-filed issues with their own fix plans expected.
