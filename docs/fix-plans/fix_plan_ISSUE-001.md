## 1. Remediation approach

Apply the catalog's CWE-770 canonical_approach (replace an unbounded read with a paginated or server-filtered query) to the sheduler-service manifestation of this issue. EmployeeSchedulerServiceImpl.getAllEmployees() switches from repository.findAll() to repository.findAll(PageRequest.of(0, MAX_PAGE_SIZE)) with a fixed server-side cap, so the REST endpoint's cost is bounded regardless of collection size -- this satisfies the issue's own Expected Behavior ('read operations that back a REST endpoint should return a bounded result set'). Separately, WomenDaySchedulerImpl currently loads the same unbounded getAllEmployees() and filters for GenderType.FEMALE in Java after the full load -- that is corrected by pushing the filter into the database via a new Spring Data derived query, findByGender(GenderType), so the job's own working set is bounded by how many female employees actually exist rather than by the whole collection. Capping the shared getAllEmployees() method would have silently truncated the Women's Day job's results (it would only see female employees within the first page), which is why the job is switched to its own dedicated, correctly-filtered query instead of reusing the capped method.

**Catalog pattern (`CWE-770`):** Allocation of Resources Without Limits or Throttling

## 2. Alternatives considered

- Capping getAllEmployees() and having WomenDaySchedulerImpl keep filtering the capped result in Java -- rejected: this would silently make the Women's Day job incomplete/incorrect once the collection exceeds the page cap, trading an availability bug for a correctness bug.
- Exposing page/size query parameters on GET /api/v1/employee so callers control pagination -- rejected for this diff as larger than necessary: it requires changing the controller's public contract and the service interface signature, not just bounding the existing unbounded call. Recorded as a reasonable follow-up, not done here.
- Fixing report-service's identical findAll() pattern in the same diff -- rejected: report-service's export path needs the complete dataset (it is a payroll export, not a listing endpoint), so the correct fix there is streaming/chunked processing rather than pagination that would truncate payroll output. That is a materially different, larger change and belongs in its own fix plan (see Risks to watch).

## 4. Risks to watch

- GET /api/v1/employee's response will now cap at MAX_PAGE_SIZE (500) records instead of returning literally everyone -- this is the issue's own requested behaviour, but any caller currently depending on getting the true full collection from this single call will need to switch to a real paginated contract in a follow-up.
- report-service's EmployeeReportServiceImpl.getEmployees() has the same root cause but needs a streaming fix, not pagination, because the export must include every employee -- this remains open and should be tracked as its own fix.
- The Women's Day job's output changes from 'first N employees who happen to be female, if within a capped page' (if it had reused the capped method) to 'every female employee' (via the dedicated query) -- this is a correctness improvement, not a regression, but is worth calling out since the job's actual output set changes.
