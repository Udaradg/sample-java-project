## 1. Remediation approach

This issue's true scope spans 6 independently-deployed modules plus 2 infrastructure services, which is not a single reviewable diff -- adding Spring Security to six separately-versioned Maven modules, each with its own filter chain, credential handling and test impact, is 6-8 separate changes by any reasonable reading of 'smallest diff'. This plan scopes to the single highest-value, self-contained starting point: employee-service, which hosts the richest PII surface (read-one, search, create, bulk-upload) among the affected services. Adding spring-boot-starter-security with no custom SecurityFilterChain is the smallest possible closure of CWE-306 here: Spring Boot's own auto-configuration then requires HTTP Basic authentication for every request by default (secure-by-default), with no new Java class needed. A fixed interim credential is set via application.properties (environment-overridable) rather than relying on Spring Boot's auto-generated random password, since a password that changes every restart and is only visible in logs is not a usable interim control. In the same file the committed TRACE override that force-enables full-entity logging is disabled, and the one call site that logs the entire Employee object (exposing address and phone via Lombok's toString()) is changed to log only the employee id -- closing the employee-service-specific instance of CWE-532 the root cause report identified as call site 3.

**Catalog pattern (`CWE-306`):** Missing Authentication for Critical Function

## 2. Alternatives considered

- A hand-written SecurityFilterChain bean with explicit authorizeHttpRequests rules -- rejected for this smallest-diff pass: Spring Boot's zero-configuration default (deny-all-without-auth once the starter is present) already satisfies the issue's Expected Behavior ('every endpoint... must require an authenticated principal') without a new class. A follow-up can add fine-grained rules (e.g. permitting only /actuator/health anonymously) once the interim credential is replaced with real identity-provider integration.
- Fixing all 6 services (plus configuaration-server and discovery-service) in one diff -- rejected as far larger than a reviewable single change; each service needs its own dependency addition, credential handling and verification, and the blast radius report already shows every service is independently broken, not chained, so there is no correctness reason they must ship together.
- Projecting EmployeeController's responses into DTOs instead of the raw entity (CWE-200, also named in the root cause report) -- rejected for this diff: it is a separate, independent defect class from 'nobody is authenticated at all', and folding it in here would make the diff larger without being necessary to close CWE-306. Recorded as a follow-up.

## 4. Risks to watch

- Every existing client of employee-service's endpoints (other services, test suites, manual callers) will need the interim credential once this ships -- this is a deliberate, intended breaking change (the endpoints are supposed to stop being anonymous), but it must be communicated/rolled out, not silently deployed.
- The interim fixed credential is a stopgap, not a real access-control model (no per-user identity, no audit trail) -- it satisfies 'requires authentication' but not the issue's further request for per-principal authorization and an audit trail, which need real identity-provider integration as a follow-up.
- report-service, sheduler-service, department-service, configuaration-server and discovery-service all have the identical missing-authentication defect and are explicitly NOT addressed by this diff -- each needs its own, separately-tracked fix plan.
- Actuator's /actuator endpoints (already exposed via spring-boot-starter-actuator) will also start requiring authentication once Spring Security is added, since no explicit permit-all rule is added in this smallest-diff pass -- flag this if any external health-check monitoring depends on unauthenticated access.

## 5. How the fix must be verified

1. Compile employee-service.
2. Confirm a request to any /api/v1/employee/** endpoint without credentials now returns 401 instead of the previous 200/201.
3. Confirm the same request with the configured interim credential succeeds as before.
4. Confirm the TRACE log line for createEmployee no longer prints address/phoneNo, only the employee id.
